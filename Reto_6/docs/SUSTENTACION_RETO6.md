# Sustentación del Reto 6 desde el API Gateway

## Preparación

En `Reto_6`, cree `.env` a partir de `.env.example`, ajuste los secretos locales y compruebe que `E2E_ADMIN_PASSWORD` corresponde a `ADMIN_PASSWORD_HASH`. Levante el sistema con `docker compose up --build -d --wait --wait-timeout 300`. El único puerto HTTP de negocio publicado es `http://localhost:8080`; RabbitMQ Management está en `http://localhost:15672`. Mantenga abierto [el Swagger del Gateway](http://localhost:8080/docs). El OpenAPI consolidado se obtiene en `/openapi.json` y ReDoc en `/redoc`.

En Swagger, pulse **Try it out**, complete el JSON y pulse **Execute**. En **Authorize** pegue solo el JWT devuelto en `access_token`: Swagger añade el prefijo `Bearer` automáticamente. Para observar un `401`, pulse **Authorize → Logout** antes de llamar una ruta protegida. Para observar `403`, autorice con el token USER. Los cuerpos, códigos y encabezados reales aparecen bajo **Server response**. Use identificadores, números y correos nuevos en cada exposición, porque el retiro conserva datos para auditoría.

## Secuencia de exposición

1. Muestre `/docs`: grupos Auth, Empleados, Departamentos, Perfiles, Notificaciones y Vacaciones, modelos y `BearerAuth`. Abra `/health` (`200`), `/redoc` y `/openapi.json`.
2. En `POST /auth/login`, envíe `{"email":"<ADMIN_EMAIL>","password":"<contraseña correspondiente al hash>"}`. Debe responder `200` con `access_token`, `token_type` y `expires_in`. El rol `ADMIN` está en el claim `role` del JWT, **no** en un campo de la respuesta. Guarde el token fuera del repositorio.
3. Sin autorizar, ejecute `GET /empleados`: debe mostrar `401` y `Bearer access token requerido`. Autorice con `Bearer` de texto alterado: debe mostrar `401` y `Access token inválido`. Después autorice con el JWT ADMIN válido.
4. Cree un departamento con `POST /departamentos`, por ejemplo `{"id":"DEMO-<sufijo>","nombre":"Calidad","descripcion":"Sustentación"}`. Debe responder `201`; confirme con `GET /departamentos/{id}` (`200`).
5. Cree un empleado con `POST /empleados`. Ejemplo: `{"id":"EMP-<sufijo>","nombre":"Ana","apellido":"Prueba","email":"ana-<sufijo>@example.test","numeroEmpleado":"N-<sufijo>","cargo":"Analista","area":"Calidad","departamentoId":"DEMO-<sufijo>","fechaIngreso":"2026-01-01","estado":"ACTIVO"}`. Debe responder `201` y publicar `empleado.creado`. Si Departamentos no responde, el contrato permite `202` y estado `PENDIENTE`; ese caso no sirve para demostrar activación.
6. Consulte `GET /empleados/{id}`, `GET /perfiles/{empleadoId}` y `GET /notificaciones/{empleadoId}`. Repita las lecturas hasta ver la proyección y una notificación `SEGURIDAD` con mensaje de cuenta creada. Las proyecciones son eventuales; no use una espera fija. Auth no expone una ruta de consulta de cuentas. Con ADMIN, use `GET /notificaciones/seguridad/{id}/token`, donde `{id}` es el ID de esa notificación. La respuesta contiene el token de activación simulado; no lo proyecte ni lo guarde en capturas públicas.
7. En `POST /auth/reset-password`, envíe `{"token":"<token de activación>","newPassword":"<clave nueva que cumpla la política>"}`. Debe responder `200` y publicar `cuenta.activada`. Haga `POST /auth/login` con el correo creado y la clave nueva; debe responder `200` con token USER. El rol USER también está en el JWT.
8. Autorice con USER. `GET /empleados` y `GET /perfiles/{su-id}` responden `200`. `PUT /perfiles/{su-id}` permite editar `telefono`, `direccion`, `ciudad` y `biografia` (`200`). `PUT /perfiles/{otro-id}`, `POST /empleados` y `DELETE /empleados/{su-id}?motivo=RENUNCIA` responden `403`. Vuelva a autorizar con ADMIN.
9. Programe vacaciones futuras con `POST /vacaciones`, por ejemplo `{"empleadoId":"EMP-<sufijo>","fechaInicio":"<fecha UTC futura>","fechaFin":"<fecha UTC posterior>"}`. Debe responder `201`; consulte `GET /vacaciones?empleadoId=...` y las notificaciones hasta ver la confirmación de `vacaciones.programadas`.
10. Pruebe errores reales: fin anterior al inicio, comienzo pasado y solapamiento responden `400`; campos ausentes o tipos incorrectos pueden producir `400` en ASP.NET Minimal API. No anuncie `409` para solapamiento: este servicio devuelve `400`. Una ID de vacaciones duplicada también devuelve `400`.
11. Para el ciclo del scheduler, use otro empleado activo y `fechaInicio = fechaFin = fecha UTC de hoy`. Espere por consulta repetida de notificaciones a la suspensión por `vacaciones.iniciadas`/`cuenta.desactivada`; entonces `POST /auth/login` del USER devuelve `401`. Espere la notificación de fin por `vacaciones.finalizadas`/`cuenta.activada` y repita login: `200`. Con intervalo de scheduler de 5 segundos, las pruebas BDD automatizan este polling. El estado intermedio puede durar poco para una demostración manual.
12. Retire al empleado con `DELETE /empleados/{id}?motivo=RENUNCIA`: `200`, `estado=RETIRADO` y `fechaRetiro` poblada. Confirme con `GET /empleados/{id}` y `GET /empleados?estado=RETIRADO`. Espere la notificación de retiro y desactivación. El login posterior devuelve `401`. `POST /auth/recover-password` devuelve deliberadamente `202` genérico incluso para retirados y no crea un token nuevo. El escenario BDD de retiro durante vacaciones verifica que el fin no reactive la cuenta.
13. Abra `e2e-tests/reports/cucumber.html` y los XML/JSON indicados en [resultados](RESULTADOS_EJECUCION_RETO6.md). Muestre características, escenarios, pasos y estados. Cada corrida BDD consulta el Gateway real.

## Límites del contrato

Departamentos no ofrece actualizar ni eliminar. Perfiles no tiene ruta `/me` ni ruta HTTP para archivar: archiva por evento de retiro. Empleados no tiene ruta de búsqueda individual por email o número; el filtro disponible es `estado` y, para `RETIRADO`, `desde`/`hasta`. Vacaciones no expone un disparador HTTP del scheduler. La recuperación de contraseña es pública y responde genéricamente para evitar enumerar cuentas. La notificación de seguridad es un mecanismo simulado de entrega, accesible solo a ADMIN mientras el token está vigente.
